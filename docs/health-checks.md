# 设备业务健康检查

在「设备总览」每台设备的「健康检查」中新增、编辑、启停或删除检查，点击「保存配置」后生效。配置持久保存在服务端，设备离线也可保存，上线后自动下发。管理员和设备范围内的运维可以修改及立即探测；业务和审计账号仅能查看授权范围内的配置与结果。

探测由目标设备的 Agent 执行，因此 `127.0.0.1` 指目标设备本身。现支持：

- HTTP/HTTPS：GET 请求，检查预期状态码，可选检查响应包含文本。校验系统信任的 TLS 证书，不跟随重定向，不使用代理，不支持 URL 账号密码；正文检查最多读取 64 KiB，不上传正文。
- TCP：检查主机名或 IP 的指定端口是否能建立连接，不发送应用数据。
- systemd：通过 `systemctl is-active` 只读检查 `.service` 单元，不启动或重启服务。没有 systemd 或无法读取服务状态时为未知。参数独立传入，不通过 Shell，不提权。

每台设备最多 8 项；周期 5–3600 秒，超时 100–30000 毫秒且不得超过周期，失败阈值 1–10 次。Agent 最多同时执行 4 项，每项不会重叠执行。保存、重新连接后立即开始新一轮；「立即探测」提前触发检查，执行期间的重复请求合并。持续检查不阻塞控制心跳、命令或终端。

所有启用项都健康时，设备业务健康为健康；任一项连续失败达到阈值时为异常；未配置、全部停用、尚未得到结果、结果过期、设备离线或 Agent 不支持探测时为未知。阈值前的失败保留最近的有效健康状态，没有历史成功时保持未知；一次成功即可恢复健康并清零失败计数。结果超过 `max(15秒, 2×周期+超时)` 未更新后失效；重新连接须收到本次连接的新结果才生效。业务健康不表示 EasyTier 私网可达，私网可达仍未采集。

配置使用递增 revision 防止并发覆盖。Agent 只执行严格校验的探测类型；旧 revision、重复或乱序结果不能改变当前配置的状态。配置更新、请求立即探测写入平台审计；周期探测保存最近结果，不产生无限历史。前端每 3 秒更新打开的检查面板，设备列表沿用 10 秒刷新。

API：`GET /api/v1/devices/:id/health-checks` 返回配置及最近结果；`PUT` 同路径提交 `{v:1,revision,checks}`；`POST /api/v1/devices/:id/health-checks/run` 提交 `{v:1,revision}`。每个检查有 id、名称、启用状态、周期、超时、阈值及带类型的 probe。配置修改和立即探测要求 Bearer 运维权限。旧 Agent 可继续使用原有控制与 Exec；更新支持 `health.probes.v1` 后才下发探测配置。

浏览器验证：已有本地服务端、Linux Agent 容器和 Chromium 时，设置 `FLEET_CREDENTIALS_FILE`、`PLAYWRIGHT_BROWSERS_PATH` 后运行 `npm run test:health:browser`。该检查在开发容器内启动临时回环 HTTP 服务，验证前端配置、真实 Rust 探测、失败阈值、恢复、TCP、systemd 缺失、停用、删除和移动布局，结束后移除本次测试配置及临时服务。

2026-10-15 本地验证：服务端 13/13、前端 32/32、协议 145/145、Linux Rust 29/29（27 单元及进程测试、2 契约测试）通过，前后端构建、Rust clippy 与格式检查通过。健康检查 Chromium 流程和原有终端/免密 sudo/关闭/录制回放回归通过。结果文件为 `.test-output/health-browser.json`、`health-rust.log`、`health-server.log`、`health-contracts.log` 及截图。开发容器没有运行 systemd，验证了缺失时保持未知；真实 systemd 主机上的活动/停止服务仍需现场验证。这些结果不是 CI、压力或生产验收。
